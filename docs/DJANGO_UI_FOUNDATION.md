# Django UI Foundation (Phase 3)

Status: current-state document, established 2026-09-20. This is the Phase 3
UI foundation for the clab_dualstack_lab project: a Django human control
plane shell with no deep network automation logic. It supersedes nothing —
no prior Django code existed in this repository before this phase (searched
for `manage.py`/`settings.py`/`urls.py`/`views.py`/Django imports across the
whole repo; the only hits were NetBox's own vendored Django, in
`netbox/scripts/ensure_api_token.py` and `netbox/configuration/
configuration.py` — that is NetBox's internal implementation detail, not
part of this project's own web application, and was not touched).

## 1. Project/app structure

```
web/                          # Django project root (new in Phase 3)
    manage.py
    requirements.txt          # Django>=5.1,<5.2 — the only new dependency
    db.sqlite3                # gitignored; holds only Django's own admin/auth/session tables
    config/                   # Django project package
        settings.py
        urls.py
        wsgi.py
        asgi.py
    core/                     # the one app implementing the Phase 3 shell
        views.py              # thin adapters: one service call + one render, nothing else
        urls.py
        theme_registry.py     # source of truth for themes/contexts/page mapping
        theme_assets.py       # artwork slot -> static URL resolution, graceful fallback
        context_processors.py # injects theme/page state into every template
        services/             # the service boundary (see §7)
        templatetags/core_extras.py
        templates/core/       # base.html + one template per page + components/
        static/core/          # css/, js/, themes/ (artwork slots)
        tests/                # 50 tests across 6 files (see §11)
```

Everything else in the repository (`modules/`, `monitoring/`, `netbox/`,
`templates/`, `master.py`) is untouched. `web/` coexists alongside them as a
sibling directory at the repo root — nothing was moved to make room for it.

`DJANGO_DEBUG=true` is required for local development (see §9 — DEBUG

DJANGO_DEBUG=true /home/student/Scripts/.venv/bin/python3 manage.py migrate

`migrate` only creates Django's own `auth`/`admin`/`sessions`/`contenttypes`
tables — Phase 3 adds no models of its own (see §6 on why theme state is a
cookie, not a table).

## 3. Dependency installation

`web/requirements.txt` contains exactly `Django>=5.1,<5.2`, installed into

## 5. Sidebar/header architecture

The sidebar (`core/templates/core/base.html`) renders exactly five links —
Home, Monitoring, Device Builder, NSOT, Automation — driven by a plain list
in the template, not a loop over a longer config that might accidentally
grow. `core/context_processors.py` maps the current URL name to a
`page_key`, and the sidebar link for that key gets `.is-active`. Below
900px, the sidebar becomes an off-canvas panel toggled by a hamburger button
(`core/static/core/js/app.js`), which is the only JS-driven layout behavior
in the app.

The header (`core/templates/core/components/header.html`) holds, left to
right: a mobile sidebar toggle, the page title, a theme `<select>`, the
notification bell, and the profile avatar. Notification and profile are
implemented as small dropdown panels (`components/notification_dropdown.html`,
`components/profile_menu.html`) toggled by `app.js`; both link to their own
routable, non-sidebar pages. This satisfies the Phase 3 requirement that
Notifications and Profile exist and are reachable, but never appear in the
left navigation — enforced by `core/tests/test_navigation.py` and
`test_routes.py`, which parse the rendered sidebar markup and assert neither
URL is present there.

## 6. Service-layer boundary

Every view in `core/views.py` calls exactly one function in `core/services/`
and renders a template — no view imports `netmiko`, `pynetbox`, `paramiko`,
`subprocess`, or an InfluxDB client (enforced by
`core/tests/test_architecture.py`, which parses `views.py`'s AST and asserts
none of those modules are imported).

| Module | Future integration point (not called yet) |
|---|---|
| `services/topology_service.py` | `monitoring/scripts/topology_server.py`'s `GET /api/topology` (127.0.0.1:8050) — Phase 5 |
| `services/monitoring_service.py` | Grafana at 127.0.0.1:3000 (loopback-only) — Phase 6 |
| `services/nsot_service.py` | `modules/netbox_ipam.py` (pynetbox), never NetBox directly — Phase 7 |
| `services/device_builder_service.py` | device intent capture / candidate config generation — Phases 8/9 |
| `services/automation_service.py` | fleet health / change mgmt / rollback / soak / history / troubleshooting — later phases |
| `services/notification_service.py` | a real notification/event backend — Phase 4 |

Every summary function returns `{"status": "not_integrated", "message":
"..."}` (`core/services/base.py:not_integrated()`) rather than fabricated
operational data — `test_services.py` asserts none of them carry
look-like-real keys such as `devices_up`/`cpu_percent`. The one exception is
`monitoring_service.CANONICAL_DASHBOARDS`, which reproduces the
already-published, non-secret Grafana UID/title table from
`docs/GRAFANA_MONITORING_TAXONOMY.md` §8 — safe metadata, not a live query.

## 7. Theme architecture

`core/theme_registry.py` is the single source of truth: `THEMES` (a dict of
the four top-level themes and their contextual variants),
`PAGE_THEME_CONTEXT` (which context each theme uses on each page), and
`resolve_theme()`/`resolve_context()` (fallback-safe lookups). Nothing else
hardcodes a theme or context name — templates and CSS both key off
`data-theme`/`data-theme-context` attributes on `<html>`, set from this
registry via `core/context_processors.py:theme_context()`.

### Registry

| Theme | Contexts |
|---|---|
| Basic Minimal | `default` |
| Dark Mode | `default` |
| Dark Angels | `core`, `deathwing`, `ravenwing`, `hexagrammaton` |
| Adeptus Mechanicus | `core`, `forge`, `monitoring` |

Dark Angels and Adeptus Mechanicus are each **one** top-level theme with
several contexts — never four/three separate themes — matching the Phase 3
spec exactly (`test_themes.py::ThemeRegistryTests` asserts the theme set has
exactly 4 members and each variant set is exact).

### CSS / design tokens

`core/static/core/css/tokens.css` defines CSS custom properties on `:root`
(Basic Minimal defaults), then overrides only what changes under
`[data-theme="..."]` and `[data-theme="..."][data-theme-context="..."]`
selectors. A contextual variant therefore only overrides its accent/
background/watermark-strength tokens, never the whole palette — proving each
Dark Angels/Mechanicus variant is a variant, not an independent theme.
`core/static/core/css/base.css` is the component library (layout, sidebar,
header, dropdowns, cards, badges, buttons, forms, tables, tabs, alerts,
modal shell, empty state, code/log/diff panels) and reads only these tokens
— no component hardcodes a color.

### Page-context mapping (demonstrated in Phase 3)

| Page | Dark Angels | Adeptus Mechanicus |
|---|---|---|
| Home | Core | Core |
| Monitoring (+ subpages) | Ravenwing | Data/Monitoring |
| Device Builder | Core | Forge |
| NSOT | Hexagrammaton | Core |
| Automation (+ sections) | Core | Forge |
| Notifications | Ravenwing | Data/Monitoring |
| Profile | Core | Core |

Selecting Dark Angels and navigating from Home to Monitoring changes
`data-theme-context` from `core` to `ravenwing` without touching the
`nmas_theme` cookie — verified live (`curl -b nmas_theme=dark-angels` against
`/` vs `/monitoring/`, see §12) and by
`test_themes.py::ThemePersistenceTests::
test_page_context_switches_without_changing_persisted_theme_cookie`.

### Persistence

Theme choice is stored in a plain browser cookie (`nmas_theme`,
`settings.THEME_COOKIE_NAME`, 1-year max-age), set by a small POST-only view
(`core/views.py:set_theme`, CSRF-protected) and read back by
`context_processors.theme_context()` on every request. **No database model
or migration was added for this.** With no authentication/account system
yet in Phase 3, a per-user database-backed preference would be premature —
the brief explicitly calls this out. A cookie is lightweight, works for
anonymous visitors, is trivially testable with Django's test client (see
`test_themes.py`), and can be swapped for a user-profile field once accounts
exist without changing the registry or templates — only
`context_processors.py`'s cookie read would need to also check
`request.user`.

### Fallback behavior

`theme_registry.resolve_theme()` returns `"basic-minimal"` for any value not
in `THEMES` (unknown cookie, missing cookie, empty string). Verified both as
a unit test and live over HTTP with a bogus cookie value (§12).

## 8. Artwork assets

**The ten operator-supplied UI/UX artwork assets were not found.** Searched:
the entire repository tree, `~/Pictures`, `~/Downloads`, `~/Desktop`,
`~/Documents`, and the Codex/Claude attachment caches under
`~/.codex/attachments/*` (eight directories found, each containing only a
`pasted-text.txt` — no images anywhere). No substitute artwork was generated
or downloaded, per instructions.

Per the phase's explicit fallback instruction, the complete static-asset
framework was still built:

- `core/theme_assets.py` defines `ASSET_SLOTS` (ten named slots) and
  `resolve_watermark_url(slot)`, which looks for
  `core/themes/<slot>/watermark.{svg,png,webp,jpg,jpeg}` via Django's
  staticfiles finders and returns `None` if nothing is there yet.
- `core/static/core/themes/<slot>/` directories exist (with `.gitkeep`
  placeholders) for all ten slots; `core/static/core/themes/README.md`
  documents exactly where each of the ten files should be dropped and its
  suggested filename.
- Every template falls back to a CSS-only gradient/circuit-pattern
  background (`.theme-watermark--fallback` in `base.css`) when
  `resolve_watermark_url()` returns `None` — verified live and by
  `test_themes.py::ArtworkFallbackTests`.

| Slot | Directory | Suggested subject |
|---|---|---|
| Global brand mark | `core/themes/brand/` | app identity mark (header) |
| Basic Minimal | `core/themes/minimal/` | subtle circuit motif |
| Dark Mode | `core/themes/dark/` | restrained NOC/console motif |
| Dark Angels — Core | `core/themes/dark_angels/core/` | Lion/knightly-helm watermark |
| Dark Angels — Deathwing | `core/themes/dark_angels/deathwing/` | terminator-helm watermark |
| Dark Angels — Ravenwing | `core/themes/dark_angels/ravenwing/` | Ravenwing watermark |
| Dark Angels — Hexagrammaton | `core/themes/dark_angels/hexagrammaton/` | six-part radial/heraldic motif |
| Mechanicus — Core | `core/themes/mechanicus/core/` | cog/cogitator mark |
| Mechanicus — Forge | `core/themes/mechanicus/forge/` | forge/industrial motif |
| Mechanicus — Monitoring | `core/themes/mechanicus/monitoring/` | data/scan-line motif |

This ten-slot layout (1 global + 1 + 1 + 4 + 3 = 10) is this foundation's
best-effort inference from the Phase 3 theme/variant list, **not** a
confirmed mapping to the operator's real ten filenames — confirm/adjust when
the actual files are supplied. No renaming, recompression, or resizing is
needed on arrival: drop each file in as `watermark.<ext>` (any of the five
extensions checked) and it is picked up automatically, with the browser/CSS
handling sizing. Phase 20.5 expands the independent background layer to
`min(94%, 1280px) auto` on desktop and `96% auto` on narrow screens, with
`no-repeat`, a top-center offset, and the existing low-opacity token. The
profile/avatar circle remains a separate header element.

## 9. Security

| Control | Behavior |
|---|---|
| `DEBUG` | `DJANGO_DEBUG` env var, **defaults to `False`** (secure-by-default; must be explicitly enabled for local dev) |
| `SECRET_KEY` | `DJANGO_SECRET_KEY` env var; if unset **and** `DEBUG=False`, `manage.py` raises `ImproperlyConfigured` immediately (verified live, §12) rather than falling back silently. If unset and `DEBUG=True`, an obviously-fake `django-insecure-...` value is used, matching Django's own `startproject` convention. |
| `ALLOWED_HOSTS` | `DJANGO_ALLOWED_HOSTS` (comma-separated) env var; defaults to `["127.0.0.1", "localhost"]` only when `DEBUG=True`, otherwise `[]` (fails closed) |
| CSRF | Default `CsrfViewMiddleware` untouched; the one POST endpoint (`/theme/set/`) is CSRF-protected — verified live (POST without a token returns 403, §12) |
| Credentials in templates/JS | None. No NetBox/Grafana/InfluxDB/device credential ever reaches a template context, a static file, or a browser-visible value. `services/monitoring_service.py` embeds only public dashboard UID/title strings, already published in `docs/GRAFANA_MONITORING_TAXONOMY.md`. |
| Database | SQLite, holds only Django's own `auth`/`admin`/`sessions` tables — no application/network data |

No new secret-management subsystem was introduced; `web/db.sqlite3` and
`web/staticfiles/` are gitignored alongside the existing NetBox/monitoring
runtime-secret patterns in `.gitignore`.

## 10. Known limitations (explicit Phase 3 boundaries)

- No live topology (Phase 5), no Grafana embedding (Phase 6), no NetBox
  aggregation (Phase 7), no Device Builder logic (Phases 8/9), no
  Automation orchestration, no notification backend (Phase 4), no accounts/
  AAA/MFA. Every one of these is represented by an explicit
  `not_integrated` placeholder or a disabled "Not implemented in this
  phase" control — never a silently-broken button.
- The ten real artwork assets are absent (§8); the CSS fallback is
  deliberately generic (gradient + subtle diagonal hatch), not themed
  faction art, since generating substitute artwork was explicitly
  disallowed.
- Theme persistence is a cookie, not a per-user database preference (§7) —
  intentional for Phase 3's no-accounts state, flagged here so a future
  accounts phase knows to reconcile it deliberately rather than by accident.
- `web/` currently has no CI wiring (matches the rest of the repository,
  which also has no `.github/` workflows yet).
