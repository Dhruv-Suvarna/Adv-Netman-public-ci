# Version 2 Phase 1 — website identity, RBAC, website MFA, audit, hosting, capability framework

Scope: the **NMAS website** only. Nothing here touches network-device configuration, device credentials, device MFA
(privacyIDEA / RADIUS / `DeviceLoginMfaPolicy`), NetBox data, VLAN 200 or the Containerlab topology.

Two validation systems stay distinct:

* **Tier-3** (`tier3.py`, GitHub Actions) validates the NMAS application/source itself — this phase is validated by it.
* **Network-configuration validation** (V2 Phase 2+) validates device configurations. This phase only adds the
  `CONFIG_VALIDATION` axis to the capability framework so Phase 2 can record its coverage.

## 1. Authentication

* Django's own auth (users, PBKDF2 hashes, DB sessions). Login `GET/POST /accounts/login/`, logout `POST /accounts/logout/`
  (GET is refused).
* `core.middleware.NmasAccessMiddleware` is the single enforcement point: every routed `core:` request needs an
  authenticated session, then completed website MFA, then the route's permission. Anonymous page requests redirect to the
  login page; anonymous JSON requests get 401.
* Public routes (justified in `policy.PUBLIC_ROUTES`): the login page and `/healthz` (constant `ok`, no DB access).
* Login throttling: after `NMAS_LOGIN_FAILURE_LIMIT` (5) failures per username in `NMAS_LOGIN_FAILURE_WINDOW_SECONDS`
  (900 s), or 3× that per source IP, the form refuses before checking the password. Counted from the audit ledger, so it
  holds across Gunicorn workers.
* Sessions: cookie `nmas_sessionid`, HttpOnly, SameSite=Lax, 8 h, expire at browser close; `Secure` when
  `DJANGO_SESSION_COOKIE_SECURE=true` (set once every browser path is HTTPS). Open redirects (`next=`, theme `next`) are
  refused.
* Django admin keeps its own staff check **and** requires website MFA once a user is signed in.

### Bootstrap / avoiding lock-out

```bash
cd <deploy-root>/web
python manage.py nmas_grant_roles --username <operator> --all-roles --create --staff   # prompts for the password
```

The operator signs in, is sent to **Set up Microsoft Authenticator**, scans the QR code, enters the code, and is in.
Console recovery always remains: `manage.py nmas_app_mfa_reset --username <u> --confirm` (MFA) and
`manage.py changepassword <u>` (password). The local Apache vhost and `127.0.0.1:8002` (Gunicorn) stay reachable from
the host console.

## 2. Authorization (RBAC)

Django permissions on the unmanaged `core.NmasAccess` model, bundled into groups by migration 0019:

| Group | Permissions |
|---|---|
| NMAS Viewer | `nmas_view` |
| NMAS Operator | `nmas_view`, `nmas_edit`, `nmas_validate`, `nmas_plan` |
| NMAS Approver | `nmas_view`, `nmas_approve` |
| NMAS Executor | `nmas_view`, `nmas_execute` |
| NMAS Security Admin | `nmas_view`, `nmas_security_admin` |

`core/services/identity/policy.py` classifies **every** `core:` URL name exactly once (contract test): read routes need
`nmas_view` (credential status / audit log need `nmas_security_admin`); every state-changing route maps to one action —
edit, validate (validation / verification / prechecks / live checks), plan, approve (bundles, soaks, bootstrap, Golden
decisions), execute (`change_execute_run`, the only push route). Unknown routes are denied; unsafe methods on read
routes get 405. Checks use `user.has_perm` — never a username.

## 3. Website MFA (Microsoft Authenticator)

* `core/services/identity/mfa.py`: RFC 6238 TOTP through `pyotp` (SHA-1, 6 digits, 30 s — Microsoft Authenticator's
  parameters), ±1 step skew, **replay rejected** (`last_used_step`), row-locked verification, 5 failed codes sign the
  session out.
* Seed: generated by `pyotp.random_base32`, held encrypted in the session until the enrollment code is proven, stored
  encrypted (Fernet; key `NMAS_APP_MFA_KEY` or HKDF-derived from `SECRET_KEY`). Rotating `SECRET_KEY` without a dedicated
  `NMAS_APP_MFA_KEY` requires re-enrollment (admin reset).
* The QR code is an in-memory SVG data URI on a `no-store` page. Seeds, QR payloads (`otpauth://`) and codes are never
  logged, audited, committed or shown again.
* Separate lifecycle from device MFA: own model (`AppMfaDevice`, FK to the Django user only), own events
  (`APP_MFA_ENROLLED / VERIFIED / FAILED / RESET`), own recovery (`nmas_app_mfa_reset` or the Django admin action, which
  requires `nmas_security_admin`). A test proves the identity package imports no credential / device-MFA code.

## 4. Audit

One ledger: `AuditEvent`, extended (migration 0018) with `actor_user`, `request_id`, `outcome`, `http_method`, `route`,
`status_code`, `source_ip`, `user_agent`.

| Recorded | Event |
|---|---|
| login success / failure / throttled, logout (NMAS and admin login) | `AUTH_*` (Django auth signals) |
| website MFA enroll / verify / fail / reset | `APP_MFA_*` |
| every state-changing request (create / update / delete / validate / plan / approve / execute / settings) | `WEB_ACTION` with `category` |
| exports and sensitive reads (candidate download/diff, `report.json`, manifests, running-config, credential status, audit log) | `SENSITIVE_READ` |
| refusals (anonymous, missing permission, wrong method, unknown route) | `ACCESS_DENIED` |

Not recorded: static assets, ordinary page views, request bodies, field values, cookies, header values.

**Attribution.** Views pass `actor_for(request)` (the authenticated username) into services — the former hard-coded
`device-builder-operator`, `automation-workbench-operator`, `health-operator`, `execution-operator`, … labels are gone.
Non-human principals (`execution-engine`, `probation-soak-collector`, `legacy-bootstrap-collector`, scheduler
commands) keep their explicit identities. A `pre_save` receiver stamps **every** AuditEvent written during a request —
including the richer domain events (validation, plan, execution, bundle, soak) — with the request id and the
authenticated initiator, so domain events are correlated rather than duplicated. `X-Request-ID` is returned on every
response (a well-formed upstream id from Apache/Cloudflare is reused).

**Redaction** is centralized in `core/services/secret_policy.py`: `redact()` (secret-shaped keys incl. password, OTP/TOTP,
seed, recovery, CSRF, cookie/session, Authorization/bearer, RADIUS, Cloudflare, private keys, API keys, credentials;
`*_ref` stays exempt), `redact_text()` (PEM private keys, bearer tokens, `otpauth://`, GitHub/Slack tokens) and
`redact_headers()`. The pre-existing rejecting check `assert_no_secret_shaped_keys` is unchanged. Request audit keeps
only submitted field **names**.

Review: **Security → Audit** (`/security/audit/`, security admins).

## 5. Persistent hosting (Apache + Gunicorn)

See `deploy/README.md`. Gunicorn (`nmas-web.service`, systemd, autostart, restart on failure) binds `127.0.0.1:8002`.
Apache 2 (Ubuntu's `apache2`) serves `/static/` from `/var/lib/nmas/static` and proxies the rest; two loopback-only vhosts:
`127.0.0.1:80` (local / console recovery, forces `X-Forwarded-Proto: http`) and `127.0.0.1:8081` (tunnel origin, forces
`https` + HSTS). Django trusts `X-Forwarded-Proto` only with `DJANGO_BEHIND_TRUSTED_PROXY=true`, and `X-Forwarded-For`
only from `NMAS_TRUSTED_PROXY_IPS`. Runtime settings and the generated `SECRET_KEY` live in `/etc/nmas/nmas-web.env`
(0640 root:student), never in Git or unit files.

```bash
sudo deploy/scripts/install_web_stack.sh --deploy-root /home/student/Scripts/clab_dualstack_lab-deploy
```

Grafana embedding is unchanged for local browsing (`GRAFANA_BASE_URL=http://127.0.0.1:3000`). A remote (Cloudflare)
browser cannot load an iframe pointing at the server's loopback Grafana; that needs a Grafana sub-path proxy (later work).

## 6. Cloudflare (website only)

`deploy/cloudflared/` + `deploy/scripts/install_cloudflared.sh`: a named tunnel whose single ingress hostname reaches only
the Apache tunnel vhost (`127.0.0.1:8081`); everything else is `http_status:404`. No backend port is opened publicly. No
device, device DNS or device management path is involved, and website MFA stays in force behind Cloudflare (Cloudflare
Access is recommended as an additional outer layer). Account authorization (`cloudflared tunnel login`) is an interactive
operator step — see the script header for the exact sequence.

## 7. Capability framework

`core/services/capabilities/`: `axes.py` (11 axes: semantic model, Device Builder UI, renderer, config validation,
parser/import, automated tests, live read, live write, post-write validation, compensation, runtime validation),
`features.py` (one catalogue over interface kinds, routing protocols and service/policy features, each mapped to its
execution object type), `registry.py` (aggregates `platform_drivers`, `execution.capability`, the executor registry,
`config_import` and `health.live`; derives `LIVE_VERIFIED / LIVE_FAILED / LIVE_IMPLEMENTED / RENDER_ONLY /
NOT_IMPLEMENTED / UNSUPPORTED / UNKNOWN`), `evidence.py` (append-only `CapabilityEvidence` rows + audit). Live support is
never inferred from renderer support (e.g. FRR OSPF is **Render only**). The existing registries are unchanged: they
answer different questions. **V2 Phase 4** completes the matrix by calling `evidence.record_evidence(...)` with
`VERIFIED` / `FAILED` observations per axis; the page (Device Builder → Platform Capabilities → evidence matrix) updates
with no further code change.
