## Known Platform Limitations (only genuine ones)

1. **Neither live platform exposes a verified native CPU threshold SNMP trap** (cEOS 4.36.2F, Ubuntu/FRR). This is a real, unchanged platform limitation — re-confirmed, not newly discovered, during this session's CPU-threshold gap repair — and is not fabricated. `LAB_REQUIREMENTS.md` §4 "Notifications" anticipates exactly this and offers a second, explicitly accepted path ("NMAS-side threshold alerting generated from repeated CPU polls, stored as an event and clearly labelled as collector-generated rather than a device SNMP trap"), which this session implemented and live-verified (see row 4 above): `modules/cpu_alerts.py`, plugged into the existing SNMP poll path in `modules/snmp.py:collect()`, stores `collector_alert` events in InfluxDB, confirmed live this session with a real R1 CPU sample (55.6%-60.7% across six separate `--snmp-only` runs) producing a stored ALERT and RECOVERY event every run, and never labelled as a device trap. §14 item 5 is therefore satisfied by the accepted alternative path, not by a (nonexistent) native trap.
2. **cEOS-lab engineering-build `rsyslog.service` cannot start** (`improg`/`tracepointReader` `Permission denied`, an internal Arista engineering toggle, confirmed live on R1 this session: `systemctl is-active rsyslog` → `activating`). Mitigated by a direct-UDP `logger` proof (used for deterministic verification) and a best-effort supplementary forwarder. This is a platform defect, not a configuration gap, and is not concealed.
3. **cEOS AAA command-authorization/role enforcement does not work on this engineering build** (previously proven and reverted: a `network-operator`-role or custom-deny-role test user could still enter config mode). The `nmas-telemetry` account is a credential-separation control, not a functioning technical read-only boundary, on this specific image. Documented plainly in `STREAMING_TELEMETRY_IMPLEMENTATION.md`.
4. **R3/R4 have no native gNMI/NETCONF/SNMP server** — all three are repository-owned adapters/agents reading real live `/proc`, `/sys/class/net`, and SNMP-agent state. Verified live this session (adapter processes bound only to management addresses, TLS/auth enforced). Never represented as native FRR support anywhere in the docs.
5. **NETCONF is discrete retrieval only, on every platform** — cEOS 4.36.2F's NETCONF server has no notification/YANG-Push capability (confirmed: 351 capabilities enumerated, none of `:notification`/`:interleave`/`yang-push`). This is a platform capability limit, not an implementation shortfall, and is clearly distinguished from gNMI streaming throughout the documentation.
6. **H1 → WebServer application connectivity** is a pre-existing Lab-1 issue (per `AGENTS.md`/`GAP_ANALYSIS.md`). Not touched during this audit; ICMP reachability was spot-checked non-destructively in the prior audit session and succeeded (2/2, 0% loss), consistent with the issue being at the application layer, not network layer. Out of scope — did not block any mandatory Labs 2/3 verification.
7. **NETCONF SSH host-key pinning is not implemented** (`hostkey_verify=False`); stated as an accepted lab-scope limitation, not hidden.
8. **Real-link failure demonstration was not performed** (by design — disruptive link tests are prohibited without separate approval). Only the safe, clearly labelled synthetic topology demo and disposable-dummy-interface trap evidence exist (re-exercised live this session on both R3 and R4 as part of the watcher liveness-check fix below).
9. **A previously-documented intermittent verifier-side timestamp race** (`REAL_NODE_R1`/`REAL_NODE_R3` in `verify_topology.py`, comparing a cached API response against a fresh independent InfluxDB read) is noted in `DYNAMIC_TOPOLOGY.md` from a prior session. It did **not** reproduce in 3 consecutive runs performed in the prior audit session. This session's own topology regression check (run to confirm this session's SNMP/Grafana changes did not disturb topology, which is otherwise untouched by this session's work) reproduced it once in four runs (`REAL_NODE_R3` once, `REAL_NODE_R1` once, in separate runs; the other two runs passed 19/19) — consistent with it being a genuine, pre-existing, already-documented intermittent verifier-side race rather than something newly introduced, since no topology-related file was changed this session. No fix was attempted (out of scope for this CPU-threshold gap repair); see `docs/DYNAMIC_TOPOLOGY.md` for the existing analysis.
10. **R3/R4 have no init/reaper as PID 1** (`sleep infinity`, per `AGENTS.md`), so an exited monitoring helper process becomes a permanent zombie rather than being reaped. This session found and fixed one consequence: `provision_linux_snmp.py`'s link-watcher liveness check tested only `/proc/<pid>/cmdline` path *existence*, which remains true for a zombie, so a dead watcher was silently reported as "unchanged" instead of being restarted (found live on R3). Fixed to a content-based check (mirroring the already-correct adjacent `snmpd` check) plus clearing a stale pidfile before restart; re-verified live on both R3 and R4 with real disposable-dummy-interface `linkUp`/`linkDown` events, and confirmed idempotent (stable PID) across two further consecutive `--snmp-only` runs. See `docs/SNMP_IMPLEMENTATION.md` "Link-watcher liveness-check bug found and fixed". The underlying zombie-accumulation behavior itself (no init/reaper) is a genuine, unchanged platform characteristic of these containers, not something this fix eliminates — it only stops that characteristic from masking a dead watcher.
