# Phase 24 — Human 2FA with Microsoft Authenticator (design + non-live implementation)

Status (2026-09-28): **CENTRAL RUNTIME PREPARED AND FIXTURE-TESTED; R1 NOT
CONFIGURED, NOT ENFORCED, NOT LIVE-VERIFIED.** Central runtime evidence does
not authorize a device change. No R1 AAA, SSH, local user, password, routing or
interface configuration has been changed. See
`PHASE_24_R1_PILOT_REMEDIATION.md` for the source corrections and remaining
approval gates.

## 1. Decision

Select **Option A: local standards-based TOTP**.

Human administrators authenticate with a named password (knowledge) and a
six-digit RFC 6238 code generated by Microsoft Authenticator (possession).
FreeRADIUS is the EOS-facing AAA server; privacyIDEA is the local TOTP and
identity policy service. Microsoft Authenticator is enrolled as a generic
software OATH/TOTP client. It does not use Microsoft cloud push in this design.

Authoritative sources:

- [EOS 4.36.2F user security and RADIUS AAA](https://www.arista.com/en/um-eos/eos-user-security)
- [Microsoft Authenticator can generate OATH verification codes](https://learn.microsoft.com/en-us/entra/identity/authentication/concept-authentication-authenticator-app)
- [privacyIDEA `otppin=userstore` validates user-store password plus OTP](https://privacyidea.readthedocs.io/en/latest/policies/authentication.html)
- [privacyIDEA FreeRADIUS `rlm_rest` integration](https://privacyidea.readthedocs.io/en/v3.5/application_plugins/rlm_rest.html)
- [RADIUS Access-Challenge semantics, RFC 2865](https://www.freeradius.org/rfc/rfc2865.html)

This is true two-factor authentication. A username is an identifier, not a
factor. Two passwords would both be knowledge factors and are not 2FA.

No legacy functionality was deleted before dependency analysis.

## 3. Architecture comparison

### Option A — local password + TOTP (selected)

The operator types one SSH password-field value:

```text
<human password><six-digit current TOTP>
```

The TOTP code is not another password. Microsoft Authenticator can calculate it
only because the phone holds the unique per-human seed. The local server holds
the verifier copy, checks time/counter state, and rejects reused codes.

Benefits for this lab:

- no Microsoft tenant, paid MFA license, Windows Server or Internet dependency;
- works with Microsoft Authenticator's standards-based OATH/TOTP capability;
- reproducible with open local components;
- one-shot RADIUS authentication, so EOS SSH need not implement an interactive
  `Access-Challenge` conversation;
- phone can generate codes offline (server and phone clocks must remain close).

Limitations: TOTP is not phishing-resistant, concatenated input has a less
polished UX than a separate OTP prompt, and end-to-end EOS RADIUS transport is
not yet live-tested.

### Option B — Microsoft Entra / Authenticator push (not selected)

The supported Microsoft RADIUS bridge is the NPS extension. Microsoft documents
Windows Server/NPS, Active Directory user validation, an Entra tenant, an
eligible Entra MFA license, outbound HTTPS connectivity, certificate setup and
RADIUS ports. Current NPS guidance also distinguishes PAP/TOTP from push and
notes method-specific limitations.

This could provide Authenticator push, but it introduces Windows Server,
directory synchronization, cloud availability, licensing and Internet
dependencies that the university lab does not otherwise need. EOS 4.36.2F
parser support for RADIUS does not prove the complete EOS SSH → NPS → Entra push
transaction, and that transaction was not tested in this non-live phase.

Sources: [NPS extension prerequisites and licensing](https://learn.microsoft.com/en-us/azure/active-directory/authentication/howto-mfa-nps-extension),
[NPS authentication flow](https://learn.microsoft.com/en-us/entra/identity/authentication/howto-mfa-nps-extension-vpn),
and [NPS number-matching/TOTP behavior](https://learn.microsoft.com/en-us/entra/identity/authentication/how-to-mfa-number-match).

## 4. Exact authentication flows

### Human interactive SSH

1. Human SSH client sends username `ops-<person>` and the concatenated
   password+TOTP in SSH's password method.
2. EOS evaluates `aaa authentication login default local group
   NMAS-HUMAN-MFA`.
3. Human usernames **must not exist locally**, so EOS's documented service-list
   behavior advances from `local` to the named RADIUS group.
4. EOS sends a RADIUS Access-Request to `192.168.200.100:1812` from Vlan200.
5. FreeRADIUS rejects machine-only usernames from this path and passes the
   human request to privacyIDEA over authenticated TLS.
6. privacyIDEA policy `otppin=userstore` checks the password and the assigned
   TOTP token. Disabled/locked users, invalid/expired/replayed OTPs, or either
   wrong factor produce rejection.
7. On success FreeRADIUS returns Access-Accept with `Service-Type =
   NAS-Prompt-User` and `Arista-AVPair = shell:roles=network-admin`.
8. EOS opens the SSH session.

`Access-Challenge` is not required. Its EOS SSH behavior remains unproven and
must not be claimed.

### NMAS automation

1. NMAS uses the dedicated local username `nmas-automation` from source
   `192.168.200.100` with its protected, automatically rotated machine secret
   (and an optional machine-held SSH key retained from Phase 23).
2. EOS finds the local service account first and never sends it to RADIUS.
3. No phone, OTP or push is requested.

The live cEOS audit found `admin` and `nmas-telemetry`, not a verified
`nmas-automation` login account. Source now selects `nmas-automation` for R1
only, while every other cEOS device retains the fleet profile. The shared
consumer resolver covers Health, NSOT/config retrieval, configuration/removal
execution, `master.py` and `address_report.py`. R1 still reports a blocker until
the protected secret and dedicated account are created and proven during the
separately authorized rollout. This source phase does not create either.

Compensating controls:

- service-only purpose and no human sharing;
- password only in the protected runtime provider, with automatic rotation;
- optional machine private key only in that provider;
- NMAS source/network restriction where technically enforceable;
- FreeRADIUS explicitly rejects `nmas-automation` if it unexpectedly reaches
  the human backend;
- authentication/accounting logs without passwords, OTPs or seeds;
- a distinct service role and minimum command set.

The last item has a known limitation: this cEOS-lab engineering build previously
ignored role restrictions. Least privilege must be re-proved on the exact image
before rollout; credential separation is not a substitute for working command
authorization.

## 5. Central AAA deployment model

Use FreeRADIUS 3 with `rlm_rest` and privacyIDEA 3.13.4 pinned to upstream commit
`9688ada43e30b7c97b126f460aa75b92315e1dd8`. The non-live FreeRADIUS image,
site, REST module, Arista dictionary, client example and isolated compose profile
are under `monitoring/human_mfa/`. The profile has not been started and is not
included by the operational monitoring compose file.

privacyIDEA owns:

- named human identity/password verification;
- per-human TOTP tokens and encrypted seeds;
- token state, time window, replay rejection, lock/disable policy;
- enrollment and audit records.

FreeRADIUS owns:

- per-device RADIUS clients and shared secrets;
- EOS-facing Access-Request/Accept/Reject;
- denial of machine identities on the human path;
- static EOS role attributes after successful privacyIDEA authentication.

The REST integration intentionally does not use its unsupported challenge or
attribute-mapping features. TLS certificate verification is mandatory between
FreeRADIUS and privacyIDEA. FreeRADIUS 3.2.1 uses `ca_info_file` for the CA
trust bundle; the earlier tracked `ca_file` directive was incorrect and has
been remediated in source.

## 6. Enrollment

Enrollment is a later explicit runtime action:

1. create/verify the named human in the privacyIDEA user store;
2. initialize one unique TOTP token with server-generated entropy;
3. display the enrollment QR only over the protected privacyIDEA UI;
4. in Microsoft Authenticator choose a non-Microsoft/other TOTP account and scan;
5. require an initial OTP to verify enrollment before enabling the token;
6. store recovery material offline under the break-glass policy;
7. never export the seed to NMAS, Django, Git, logs, argv, screenshots or JSON.

The server-side seed, database encryption key and backups belong only in
`monitoring/runtime/human-mfa/`. Automated tests use fixed fake values and never
generate an operator seed or QR code.

## 7. EOS candidate and parser evidence

The R1 renderer separates account preparation from one atomic activation.
Secret values remain runtime provider references.

Preparation (create, then independently verify both identities before AAA):

```text
username nmas-automation privilege 15 role network-admin secret <provider:runtime://device-credentials/r1-nmas-automation>
username r1-breakglass privilege 15 role network-admin secret <provider:runtime://device-credentials/r1-breakglass>
```

Atomic activation:

```text
no username admin
radius-server host 192.168.200.100 key 0 <provider:runtime://human-mfa/radius/r1>
aaa group server radius NMAS-HUMAN-MFA
   server 192.168.200.100
ip radius source-interface Vlan200
aaa authentication login console local
aaa authentication login default local group NMAS-HUMAN-MFA
aaa authorization commands all default local
management ssh
   authentication protocol password
```

The `local`-first order is deliberate: the dedicated machine and unique sealed
break-glass accounts are handled locally; usernames absent locally continue to
RADIUS. The named human is never created locally. Existing shared `admin` is
removed in the same activation transaction so it cannot silently bypass MFA.

On 2026-09-28 the R1 EOS 4.36.2F parser accepted the RADIUS host/group/server,
Vlan200 source, console/default login lists and local command authorization in
configuration session `PHASE24_MFA_FULL_PARSE`. No `commit` was issued. The session
was explicitly aborted, disappeared from `show configuration sessions`, and the
running-config SHA-256 was identical before and after:

```text
148470d860acb4205d6ce74190737a5eb2db10311e96752266d284487af32693
```

The full candidate, including `management ssh ... password`, was present in the
uncommitted session diff. Parser acceptance does **not** prove
RADIUS packet format, TOTP success, failover or login authorization. Those are
live-rollout gates.

Rollback candidate:

```text
management ssh
   default authentication protocol
no aaa authorization commands all default local
no aaa authentication login default
no aaa authentication login console
no aaa group server radius NMAS-HUMAN-MFA
no radius-server host 192.168.200.100
no ip radius source-interface
username admin privilege 15 role network-admin secret <provider:runtime://device-credentials/ceos-admin-shared>
no username r1-breakglass
no username nmas-automation
```

Rollback removes AAA first, restores the prior shared recovery identity, then
removes both pilot-only local accounts. The R1 consumer's bounded fleet-profile
fallback then preserves automation after rollback. Rollback must still be
generated against and reviewed with the immediate pre-change configuration; it
must not blindly remove pre-existing AAA statements.

## 8. Failure and break-glass behavior

- RADIUS/privacyIDEA unavailable: central human login fails closed; existing
  local machine and emergency identities still authenticate before RADIUS.
- Bad RADIUS policy/Access-Reject: there is no fallback for a human username;
  use console/docker exec and roll back.
- Console: `docker exec -it clab-srlceos01-<node> Cli` bypasses management SSH.
- Linux console: `docker exec -it clab-srlceos01-<node> bash` bypasses sshd.
- Emergency administrator: one unique local account, long offline-held secret,
  no routine use, explicit audit/rotation after use. It is an intentional
  emergency exemption and must not be a shared daily account.
- During rollout: keep a verified console open, preserve the current working
  SSH session, test the new path before ending either, and apply one device at a
  time beginning with R1.

R3/R4 remain blocked: only root is currently available and no PAM/RADIUS change
is authorized or implemented. A dedicated non-root account and a separately
tested PAM/privacyIDEA path are prerequisites.

## 9. Non-live tests

`totp_contract.py` is an explicitly fixture-only policy oracle; it is not a
RADIUS server and contains no seed algorithm or real enrollment material. Tests
cover:

- password only: reject;
- OTP only: reject;
- wrong password + correct OTP: reject;
- correct password + wrong OTP: reject;
- correct password + correct OTP: accept;
- approved machine identity from NMAS: accept without OTP;
- human use of the machine exemption: reject;
- wrong machine source: reject;
- central AAA unavailable, expired OTP, replayed OTP, malformed input and
  disabled human: reject/unavailable as appropriate;
- output redaction and no committed seed/shared secret;
- deterministic EOS candidate, rollback and lockout blockers.

All such results are **fixture/non-live evidence**, never live enforcement.

Observed source validation on 2026-09-28 after R1 remediation:

- 129 focused Django tests passed across MFA/credentials, management entry
  points, execution/auth, Health and NSOT, plus 4 standalone per-device access
  profile tests;
- full offline Tier-3 passed with warnings: 1,481 Django tests and 471
  monitoring tests passed;
- Django system check, migration-drift, static hygiene/syntax and Grafana drift
  checks passed;
- Docker Compose rendered the isolated `human-2fa` profile successfully;
- the built FreeRADIUS 3.2.1 image reported `Configuration appears to be
  OK` under `freeradius -XC`, with no network and a test-only CA mount;
- `git diff --check` passed.

The Tier-3 warning is expected and explicitly authorized for this remediation:
`inventory.yml` changes only R1's automation identity metadata; it does not
alter topology, addressing, routing, VLANs or links. Lab-backed checks were not
run because this source-remediation phase forbids live device work.

The container configuration check proves FreeRADIUS syntax/module loading. It
does not claim that privacyIDEA is deployed, that a real token is enrolled, or
that an EOS login succeeded.

## 10. Controlled rollout gate (next phase only)

Exact first pilot: **R1**, one central named human, local machine identity
`nmas-automation`, and unique sealed local `r1-breakglass` identity. The value
`<NAMED_OPERATOR>` supplied in planning material is a placeholder; an actual
valid username is required before metadata preparation or enrollment.

Before changing R1:

1. deploy and verify the pinned privacyIDEA/FreeRADIUS stack with backups, TLS,
   time synchronization, retention and redacted logs;
2. enroll Microsoft Authenticator and prove the RADIUS factor matrix using a
   disposable fixture user, then the named pilot operator;
3. create and verify R1's restricted `nmas-automation` account from NMAS;
4. confirm all human usernames are absent locally and resolve the legacy
   `admin` bypass;
5. capture sanitized running-config/digest and tailor the rollback;
6. open console and retain an existing SSH session;
7. apply account/server lines first, test reachability, then activate the AAA
   login list;
8. prove human positive/negative cases, NMAS Health/NSOT/config retrieval,
   RADIUS outage behavior, accounting, and break-glass;
9. roll back immediately on any discrepancy.

Only after those observations may UI state move from `PLANNED` to
`CONFIGURED`, `ENFORCED`, and finally `LIVE_VERIFIED`.
