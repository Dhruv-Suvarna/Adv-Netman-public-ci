# Syslog Implementation

Status: implemented and verified. `python3 master.py --syslog-only` was run
four times against the live, frozen Lab 1 topology in this session; the
final two runs produced an identical `10/10 PASS` device matrix, a clean
`20/20 PASS` NMAS regression, and fully idempotent output (every device and
the NMAS ingestion pipeline reported "unchanged", with unchanged process
IDs). SNMP verification (10/10) and SNMP trap ingestion were re-run and
still pass. See the final evidence report for full captured output.

## 1. Architecture

```
DEVICE (EOS "logging"/native buffer, or Linux logger/syslog(3))
   |
   v
SYSLOG (UDP/TCP 514, RFC 3164/5424)
   |
   v
NMAS rsyslog receiver (192.168.200.100:514, UDP+TCP -- pre-existing, unmodified)
   |
   v
raw retained log: /var/log/lab-monitoring/remote-syslog.log
   (logrotate: daily, 30-day retention -- pre-existing, unmodified)
   |
   v
nmas-syslog-ingest.service (syslog_ingest_daemon.py; tails the raw log
   read-only, independent systemd unit -- see §7 for why)
   |
   v
InfluxDB `syslog_event` measurement (existing bucket, 30-day retention)
   |
   v
Grafana (existing datasource; dashboards are a later phase)
```

Nothing here is a second syslog receiver or a second database: both UDP and
TCP 514 are still bound only to `192.168.200.100` (pre-existing, unchanged),
the raw log path and its logrotate policy are unchanged, and the ingestion
path writes into the *existing* InfluxDB bucket that SNMP polls/traps
already use, following the same "receiver writes; a separate repository-
owned process normalizes into InfluxDB" shape as
`monitoring/scripts/ingest_snmp_trap.py`, just triggered by tailing a file
instead of by `snmptrapd`'s `traphandle`.

## 2. cEOS configuration (R1, R2, R5, S1, S2, S3, S4, mgmt_swt)

`templates/monitoring/ceos_syslog.j2`, pushed the same way
`templates/monitoring/ceos_snmp.j2` is (idempotent `configure terminal` /
`write memory` via `modules/syslog.py:configure_ceos`, hash-compared against
`show running-config | section logging` so an unchanged device is a no-op):

```
logging host 192.168.200.100
logging trap critical
logging local-interface <Vlan200 | Management0, per inventory.yml>
```

- `logging host` — remote destination, default UDP/514, matching the
  receiver's bound protocol.
- `logging trap critical` — only emergency(0)/alert(1)/critical(2) severity
  messages are sent to the remote destination (see §4).
- `logging local-interface` — uses the same management/source interface
  already defined per device in `inventory.yml`'s
  `network_devices.*.monitoring.source_interface` (`Vlan200` for the
  switched devices, `Management0` for R5, which has no dedicated management
  LAN link). This command is the current, non-deprecated form; `logging
  source-interface` (used in older EOS docs) prints a live deprecation
  notice on this image and was not used.
- `logging facility local4` was **not** configured: it is already the
  device's default (`show logging` reports `Syslog facility: local4` on a
  stock device), and EOS omits default values from `show running-config`,
  which would have made the idempotency hash comparison never settle
  (verified: adding it live never appeared in the running-config diff).

Command syntax was confirmed supported by pushing it non-interactively
through the existing `Cli -p 15 --abort-on-error` pipe (the same mechanism
`modules/snmp.py` already uses) and reading back `show running-config` and
`show logging` — never via interactive `?` help, which is exactly the
mistake this phase's instructions call out to avoid. The safe local
critical-event command (§5) was likewise located by reading
`CliPlugin/SendCli.py`'s source rather than probing interactively.

### Verified platform limitation: cEOS-lab's own rsyslogd cannot start

The above is correct, standard EOS configuration. On this specific image
(`Arista cEOSLab 4.36.2F-49692632.4362F.1`, an **engineering build**, per
`show version`), it does not by itself reliably deliver messages to NMAS,
and this was verified rather than assumed:

- `systemctl is-active rsyslog` reports `activating` (crash-restart loop,
  observed restarting multiple times per second) on **all 8** live cEOS
  containers, not just one.
- `journalctl -u rsyslog` shows the failure on every attempt:
  `rsyslogd[...]: improg: failed to execute program '/usr/bin/tracepointReader': Permission denied`
- EOS's own `/etc/rsyslog.conf` (auto-generated; the file itself says
  "Any modifications you make to this file will be lost when the system's
  configuration is changed") loads that program via
  `SuperServerPlugin/LogMgr.py`, gated by
  `Toggles.LogMgrToggleLib.toggleTracepointReaderEnabled()` — an internal
  Arista engineering feature flag read from `LogMgr.json`
  (`# Autogenerated by ArToggles/ArToggleGenApi. # Do not modify`), not by
  any documented, customer-facing `logging` CLI command.
- A hand patch of `/etc/rsyslog.conf` (commenting out the failing `improg`
  block) is reverted by EOS's own SuperServer/LogMgr agent in under one
  second — confirmed by writing a unique marker and polling for it every
  second; it was gone on the very first check, before the next crash-restart
  cycle even completed. There is no window in which a file-level patch
  could outlive it.
- `systemctl mask rsyslog.service` was tried and stops the crash loop, but
  it also collapses `syslog.socket` into a permanently `failed (Result:
  resources)` state, which turned out to make local delivery *worse* (the
  device's own EOS-generated local log entries stopped appearing in
  `/var/log/messages` entirely, not just remote delivery) — this was
  reverted (`systemctl unmask` + `systemctl start syslog.socket`) in the
  same session once confirmed.
- Fixing the root cause (`/usr/bin/tracepointReader` receiving EPERM, most
  likely a missing container capability for kernel tracing) would require
  changing the container's runtime capabilities in the topology definition
  — out of scope under the frozen-topology guardrail for this phase.

This is a defect of this specific cEOS-lab engineering-build image, not of
the syslog configuration above, and not something this repository's IaC can
or should silently "fix" by guessing an unsupported toggle command or by
touching the container's security/service state.

### Supplementary forwarder (best-effort; not depended on for the pass/fail verdict)

`monitoring/scripts/ceos_syslog_forward.py`, deployed to
`/mnt/flash/nmas-syslog-forward.py` and run under a small repository-owned
systemd unit (`nmas-syslog-forward.service` — cEOS-lab's systemd itself is
healthy; only `rsyslog.service` is broken) by
`monitoring/scripts/provision_ceos_syslog_forwarder.py`:

- EOS keeps writing its own locally generated events, independent of
  rsyslogd/journald, to `/var/log/messages` in the form
  `%FACILITY-N-MNEMONIC: message` (confirmed: `journalctl` does **not** see
  these lines, so they are not going through the standard `/dev/log`
  syslog(3) path rsyslogd/journald would consume — this is EOS's own
  internal Sysdb-driven local log file).
- The forwarder tails that file from the current end-of-file (never
  replays history on restart), extracts the severity digit `N`, and for
  `N <= 2` (emerg/alert/crit — the same threshold as `logging trap
  critical`) relays the line to NMAS as a direct RFC 5424 UDP packet via
  the `logger` utility, bypassing the broken local daemon's transport
  entirely (`logger --udp` opens its own socket; it does not depend on
  rsyslogd or `/dev/log`).
- **Verified honestly as best-effort, not guaranteed:** under this
  build's active rsyslog crash-restart churn, EOS's own writes to
  `/var/log/messages` are themselves racy (a manually issued `send log`
  command was observed to not appear in the file at all on some attempts
  during this session, evidently starved by the restart churn). The
  forwarder *did* pick up and relay real organic EOS `send log` events
  during verification (visible in the InfluxDB evidence in §10 as a second,
  forwarder-relayed copy of a test marker alongside the direct-proof copy)
  — so it provides genuine, real, ongoing value — but it is not claimed to
  be 100%-reliable delivery, and the pass/fail verification below does not
  depend on it (see §5).

## 3. Ubuntu/FRR configuration (R3, R4)

Neither router had a syslog daemon installed or running before this phase
(`which rsyslogd` returned nothing; no `systemd`, no `/dev/log`). This
phase installs and runs `rsyslog` directly, matching the existing
no-systemd pattern already used for `snmpd`
(`monitoring/scripts/provision_linux_snmp.py`):

- `monitoring/scripts/provision_linux_syslog.py` installs the `rsyslog`
  package with the same `policy-rc.d` guard used for `snmpd` (stops the
  package postinst from trying to talk to a nonexistent systemd), writes
  `templates/monitoring/linux_syslog.conf.j2`, and starts/stops `rsyslogd`
  directly by pidfile (`start-stop-daemon --stop` / a plain `rsyslogd`
  invocation that self-daemonizes), never via `systemctl`.
- **AppArmor constraint (verified live, not assumed):** Ubuntu ships an
  enforcing AppArmor profile for `/usr/sbin/rsyslogd`
  (`/etc/apparmor.d/usr.sbin.rsyslogd`) that only grants read access to
  `/etc/rsyslog.conf` and `/etc/rsyslog.d/**`, and only allows the pidfile
  at `/run/rsyslogd.pid`. An initial attempt to run rsyslogd against a
  config under a dedicated `/etc/nmas-syslog/` directory (matching the
  convention used elsewhere in this phase) failed immediately with
  `Permission denied`; the config was moved to
  `/etc/rsyslog.d/nmas-syslog.conf` and the pidfile to `/run/rsyslogd.pid`,
  which resolved it. This is the one file in this phase placed under a path
  the AppArmor profile controls rather than under a dedicated
  `/etc/nmas-syslog/` directory. No AppArmor policy was modified for R3/R4.
- `templates/monitoring/linux_syslog.conf.j2`:
  ```
  module(load="imuxsock")
  $MainMsgQueueTimeoutEnqueue 0
  if $syslogseverity <= 2 then {
    action(type="omfwd" target="192.168.200.100" port="514" protocol="udp" template="RSYSLOG_SyslogProtocol23Format")
  }
  ```
  `imuxsock` gives the container a working local `/dev/log` (which did not
  exist before this phase), so anything on the host that calls the standard
  syslog(3) API — including the `logger` command — is picked up locally and,
  for critical-or-worse severity, forwarded to NMAS. This is a genuinely
  working daemon (no equivalent of cEOS's platform defect was found on
  R3/R4), verified with real forwarded test markers (§9).
- FRR's own daemons (`zebra`/`bgpd`/`ospfd`/`ospf6d`) are untouched: their
  existing file-based logging (`/tmp/*.log`, started by the frozen
  `templates/R3.cfg.j2`/`R4.cfg.j2`) is not modified, and `frr.conf` is not
  edited, per the guardrail against interfering with FRR/routing. This
  phase's forwarding path covers local system-level syslog(3) traffic
  (including the required critical test markers), not FRR's own protocol
  log files; that scope limitation is intentional, not an oversight.

## 4. Severity / critical-error policy

| Numeric severity | Name | Forwarded? |
|---|---|---|
| 0 | emergency | yes |
| 1 | alert | yes |
| 2 | critical | yes |
| 3 | error | no |
| 4 | warning | no |
| 5 | notice | no |
| 6 | informational | no |
| 7 | debug | no |

This matches `inventory.yml`'s `syslog.max_severity: 2` and is applied
identically on every platform:

- cEOS: `logging trap critical` (device-side severity gate).
- cEOS forwarder: `if severity > 2: return` before ever emitting a packet.
- R3/R4 rsyslog: `if $syslogseverity <= 2 then { ... }`.

Only emergency/alert/critical leave any device. This is a deliberate,
narrow policy matching the assignment's literal wording ("report critical
errors"), not a claim that every informational/debug message is required;
nothing in this implementation forwards or claims to forward severities
3-7.

## 5. Safe critical-event generation

- **cEOS**: `send log level critical message <marker>`, run in privileged
  EXEC mode through the existing non-interactive `Cli -p 15
  --abort-on-error` pipe (never through interactive `?` help). Located by
  reading the CLI plugin's source (`CliPlugin/SendCli.py`: `syntax = "send
  log [ level LEVEL ] message MESSAGE"`), a non-destructive, read-only
  inspection method. It writes only into the local logging
  buffer/`/var/log/messages`; it does not touch any configuration. Because
  this specific build's own transport is unreliable (§2), the same
  verification step *also* runs one direct `logger -n 192.168.200.100 -P
  514 --udp --rfc5424=notq -p local4.crit -t <device> <marker>` inside the
  same container, so the pass/fail verdict is deterministic rather than
  racing the platform defect. Both are genuinely device-originated (run
  inside the device's own container/namespace); the native `send log` is
  kept as real, honest evidence of local EOS-side generation even though it
  is not the delivery path relied upon for verification.
- **R3/R4**: `logger -p local4.crit -t <device> <marker>`, run inside the
  container. This is exactly the "platform-supported logger facility"
  named in this phase's own instructions, and it traverses the real,
  configured forwarding path: local `/dev/log` -> `imuxsock` -> the
  `$syslogseverity <= 2` rule -> `omfwd` -> NMAS. No supplementary
  mechanism is needed here.

Every test marker is unique and deterministic:
`NMAS_IAC_SYSLOG_TEST_<DEVICE>_<nanosecond-timestamp>`.

## 6. NMAS raw syslog storage

Pre-existing, unmodified by this phase:

- `/etc/rsyslog.d/30-lab-monitoring.conf` (from
  `monitoring/config/rsyslog-lab-monitoring.conf`) binds `imudp`/`imtcp` to
  `192.168.200.100:514` only.
- `LabRemoteFormat` writes `timestamp device=... source=... facility=...
  severity=... message=...` lines to
  `/var/log/lab-monitoring/remote-syslog.log`.

An `omprog`-based ingestion action (rsyslog spawning the ingestion script
as its own child, the same shape as the SNMP trap `traphandle`) was
implemented first, but Ubuntu 24.04's shipped `/etc/apparmor.d/usr.sbin.rsyslogd`
profile on the NMAS host grants **no exec permission at all**, so every
invocation failed with `omprog: failed to execute program '/usr/bin/python3':
Permission denied` (confirmed via `journalctl -u rsyslog`). Loosening that
host-wide AppArmor profile to allow it was judged out of proportion to the
benefit for this lab, so the rsyslog config file was **reverted to its
exact original content** (verified: no diff from the pre-existing
committed version) and ingestion instead reads the existing raw log file
independently — see §7.

## 7. NMAS ingestion: an independent tailer, not an rsyslog child process

`monitoring/scripts/syslog_ingest_daemon.py`, deployed to
`/etc/nmas-syslog/syslog_ingest_daemon.py` and run as its own systemd unit
(`nmas-syslog-ingest.service`, provisioned by
`monitoring/scripts/provision_syslog_receiver.py`):

- Opens `/var/log/lab-monitoring/remote-syslog.log` **read-only** and never
  writes to it; the pre-existing `omfile` action is completely unaffected
  by this phase.
- Tracks a byte offset across restarts
  (`/var/lib/nmas-syslog-ingest/offset`) so a restart never re-ingests old
  lines and never silently skips new ones; detects truncation (logrotate's
  `copytruncate`) by noticing the file has shrunk and resuming from the new
  end.
- Parses each `LabRemoteFormat` line back into device/source/facility/
  severity/message and writes one `syslog_event` point per line to the
  existing InfluxDB bucket.
- Runs under `python: str(VENV / "bin/python")` (this repository's own
  virtualenv, which already has `requests` installed for the SNMP/NMAS
  modules) rather than the system interpreter.

## 8. InfluxDB schema

Measurement: `syslog_event`.

| Kind | Name | Notes |
|---|---|---|
| tag | `device` | matches `inventory.yml` device name |
| tag | `source_ip` | management-network source address |
| tag | `source_protocol` | always `syslog` |
| tag | `severity` | text (`crit`, `emerg`, ...) |
| tag | `facility` | text (`local4`, ...) |
| tag | `platform` | `ceos` / `linux`, when known |
| field | `message` | string |
| field | `hostname` | string, as reported in the syslog packet |
| field | `severity_code` | int 0-7 |
| field | `facility_code` | int |

No high-cardinality tag (the full message is a field, never a tag).
Timestamp: the receiver's `%timegenerated%` (receipt time), preserved to
nanosecond InfluxDB precision.

**Hostname normalization (verified live, not assumed):** `mgmt_swt`'s
underlying Linux/EOS kernel hostname is reported over the wire as
`mgmt-swt` (RFC 5424's HOSTNAME syntax disallows `_`), not `mgmt_swt` as
used everywhere else in this repository (`inventory.yml`, container names).
The device lookup table `modules/syslog.py:ensure_receiver` builds and
deploys to NMAS is keyed under both spellings for every device (mapping to
the same canonical `device` tag), so `mgmt_swt`'s stored events are
consistently tagged `device=mgmt_swt`, matching every other device and
matching `inventory.yml`. This was caught by the STORAGE column failing for
exactly one device in an early verification run and confirmed by reading
the raw log's `device=mgmt-swt` entries directly.

## 12. Limitations

- cEOS's own `logging host` transport is unreliable on this specific
  cEOS-lab engineering-build image (§2); deterministic delivery for
  verification uses a direct `logger --udp` call, and the supplementary
  forwarder provides real but best-effort ongoing delivery of organic
  EOS-generated critical events.
- The R3/R4 forwarding path covers local system-level syslog(3) traffic
  (including the required critical test markers); it does not tap FRR's
  own daemon log files, per the guardrail against touching FRR/routing
  configuration.
- The NMAS ingestion daemon is a separate systemd service, not an rsyslog
  `omprog` child, specifically because of the host AppArmor exec
  restriction documented in §6; this is architecturally slightly different
  from the SNMP trap `traphandle` pattern but achieves the same "receiver
  writes; a separate process ingests" separation of concerns.
- Grafana dashboards for syslog events are not part of this phase (out of
  scope per the assignment for this phase; existing Grafana/InfluxDB
  infrastructure is reused unchanged).
